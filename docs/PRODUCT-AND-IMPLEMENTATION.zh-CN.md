# BuildTrace：产品与实现全景说明

2026-10-23 更新：现已支持可选事项 ID、阶段、讨论过程、交付与检查、后来反馈；旧格式兼容。默认先读摘要，再按需展开完整依据。项目偏好文件由 sync 保留。新增本地 `overview`、`sync --check`，以及 `handoff`、`claude-memory`、`langchain-md`、原文与哈希 `bundle` 导出。外部平台导入和跨设备同步不因此自动完成。新的字段边界以 [事项与阅读结构](buildtrace/references/matters-and-reading.md) 为准，原有字段说明用于兼容历史。

> 这是一份可以单独交给 Claude、Codex 或其他协作者阅读的说明。读完这一个文件，就应该知道 BuildTrace 为什么存在、保存什么、怎样运行、目前做到哪里，以及哪些边界不能越过。理解本文件不需要先看仓库代码。

## 先用一分钟理解它

BuildTrace 是给 AI 辅助项目使用的“因果记忆层”。

它要保存的不是一串代码改动，而是项目为什么一步步走到今天：

```text
人的原话与假设
        ↓
Agent 当时怎样理解、准备怎样做
        ↓
实际做了什么、计划中途怎样变化
        ↓
发布、数据、反馈或外部事实发生了什么
        ↓
后来回看：原来的判断成立、被推翻、喜忧参半，还是证据仍不足
```

它解决的是 AI 做项目以后越来越明显的断层：代码、任务和部署都留下了痕迹，人的动机、判断和取舍却散落在不同对话里，还可能被上下文压缩。几周后看数据，用户知道“发生了变化”，却想不起那段时间做了什么，更难判断是哪一个动作可能带来了结果。

BuildTrace 把这些内容写进项目内的一份 Markdown 文档。Agent 负责读、判断和写回；网页看板只负责展示。数据能随 Git 保存、迁移、搜索和审查，不依赖某个浏览器缓存，也不被某一家 AI 工具锁住。

## 它为什么被做出来

作者不是工程师，读的是人文学科，长期做用户运营、社区和线下活动，也在用 vibe coding 做自己的产品。真实困难出现在复盘时：代码和发布都有记录，人的判断却散落在不同对话里，几周后很难回答“当时为什么这样做，原本期待什么，后来是否发生”。更完整的第一人称背景见[作者长文](https://mp.weixin.qq.com/s/OBF-aNReio1grgVbTYSYzg)。

产品思考可能在一个 Agent 里，代码在另一个工具里，部署记录在 Git，数据又在 GA4、Bing 或其他后台。为了回答“是哪件事让数据变了”，需要翻遍所有地方，仍然拼不出完整的因果链。

对话里还会出现很多 Git 和普通变更日志不会保存的话：

> 我觉得 Bing 来的用户大概率是日语意图。
>
> 这个阶段先不管转化，先让页面被索引到。

这些带着个人经验、审美和判断的话，才解释了项目为何采取某个方向。BuildTrace 想保住的就是这部分“人的主观性”，同时把它与 Agent 的理解、实际行动和后来结果连接起来。

## 它面向谁

核心用户是长期用 AI 做真实项目的人，尤其是独立开发者、产品、运营、增长、内容创作者和 vibe coding 用户。他们未必有完整的工程管理流程，但会持续迭代、看反馈、做数据复盘，也会在多个 Agent、多个会话和多个工具之间切换。

典型场景包括：

- 想知道某个功能当初为什么这样做，而不只是看见它何时提交；
- 做完 SEO、内容、发布或产品动作后，过一段时间回来补数据和判断；
- 新会话或新 Agent 开工前，快速恢复项目目的、近期决策和未完成回看；
- 从多个项目中找出自己反复使用的运营逻辑、审美偏好和决策方式；
- 生成团队可看的版本或脱敏公开版本，同时保留私密原话；
- Code Review 时检查实现是否真的回应了原需求，计划与实际执行哪里不同。

## 它不是什么

BuildTrace 不替代 Git、Linear、Notion、PostHog、GA4、DevOps 平台或团队知识库。

Git 擅长回答代码改了什么，任务系统擅长回答谁在何时推进什么，数据平台擅长显示指标变化。BuildTrace 保存它们通常不会同时保存的部分：人当时为什么判断、Agent 如何理解、实际行动与后续事实之间有什么证据联系。

它也不承诺自动证明因果。一个动作发生在数据上涨之前，只能说明时间上有关联。只有存在足够证据时，记录才可以说某个判断得到支持；否则应明确写成待观察、证据不足或无法判断。

它更不是完整聊天仓库。相关原话会被保存在对应项目记录中，但系统不复制所有对话，也不会声称能找回已删除、无权限或从未导出的历史。

## 产品中的四类内容

### 1. 项目的长期背景

每个项目可以写自己的“作者的话”“项目初心”“表达习惯”和“项目资料”。

“作者的话”保存项目为什么存在以及创作者真正在意什么。“项目初心”是更稳定的判断，例如面向谁、目前最重要的方向、不想做成什么。项目资料则集中放代码仓库、文档、数据看板、部署后台、设计稿和参考资料的入口。

这些是项目上下文，不是一次功能变更。

### 2. 一条条项目记录

一条记录对应一次有意义的功能、修复、设计变化、架构调整、发布、运营动作或重要决策。小到改一个错字、只跑一次格式化、没有形成判断的机械操作，不需要单独记录。

记录分开保存几层内容：

- 沟通原文：与该事项有关的用户原话，保留原有措辞和换行；
- 需求总结：Agent 当时从原话中拆出的具体事项，每项都能回指原话；
- Agent 当时理解：接到需求时真正形成的理解，不用事后更聪明的说法覆盖；
- Agent 计划：开工时准备怎样推进；
- 执行轨迹：实际做了什么、哪些步骤完成、哪些改变、哪些受阻；
- 人的假设与为什么做：动机、顾虑、预测和取舍；
- 观察计划与数据变化：看什么指标、从哪里看、多久后看、后来发生了什么；
- 结果判断：`supported`、`refuted`、`mixed`、`inconclusive` 或 `pending`；
- 决策原则：这次真实体现、可能在其他项目复用的个人做事方式；
- 依据与技术备注：文件、提交、测试、数据源、截图或外部事实。

原话、Agent 理解、计划和执行必须分开。把它们揉成一段顺滑总结，会失去“当时到底怎么想、后来为什么变了”的审计价值。

### 3. 动作结果复盘轨

对需要等待结果的动作，BuildTrace 使用同一条记录承载：

```text
人的假设 → 做了什么 → 观察计划 / 数据变化 → 后来是否成立
```

例如：

```text
假设：先优化日语搜索入口会增加自然搜索到达
动作：新增日语落地页并提交收录
观察：四周内查看 Bing / Google 的展示、点击和落地页访问
结果：展示增加，但有效访问没有同步增长
判断：mixed；收录假设得到支持，用户意图假设仍需修正
```

“上线了”不是结果，只代表动作完成。真正的结果要在之后用数据、用户反馈、发布事件或其他事实补回来。

### 4. 跨项目决策手册

一条记录如果体现了可复用判断，可以给它一个稳定的 `dp-*` ID。多个项目出现相同 ID 时，BuildTrace 可以生成个人决策手册，并回链到每个真实项目和记录。

程序不会因为两句话看起来相似就自动合并。只有稳定 ID 相同才会聚合；同一 ID 出现不同表述时会显示冲突，交给人决定是否统一。这能避免 Agent 凭空写出一套看似正确、实际没有项目证据的“个人方法论”。

## 底层架构

BuildTrace 是一个 Markdown-first、local-first 的小型系统，当前实现不需要数据库和后端服务。

```text
用户自然语言 + Agent 工作过程 + 项目证据
                         │
                         ▼
          docs/buildtrace/BUILDTRACE.md
                   唯一事实主源
                 /        |        \
                /         |         \
               ▼          ▼          ▼
        只读 Viewer   JSON / JSONL   团队 / 公开快照
                              \
                               ▼
                       跨项目决策手册
```

关键原则只有一条：所有派生物都能重新生成，也都不能反向覆盖主源。

### Markdown 为什么是主源

Markdown 可以由人直接阅读，也便于 Agent 修改、Git 审查、代码搜索和跨工具迁移。它不要求用户维护一个额外数据库，项目被复制或迁移时，记忆也跟着项目走。

项目事实只写在 `docs/buildtrace/BUILDTRACE.md`。Viewer 状态、浏览器缓存、导出的 JSON、恢复清单和决策手册都不是第二份事实源。

### 解析和校验

一个无外部运行时依赖的 Node.js 解析器把 Markdown 转成结构化对象。它识别项目初心、作者的话、资料入口、记录元数据、原话、普通分段和复盘轨中的结构化条目。

校验器会检查：

- 日期、记录 ID 和稳定原则 ID 的格式；
- 场景、来源可信度、可见范围和结果状态是否为允许值；
- 依据及必需段落是否存在；
- “待观察”记录是否有合法的回看日期；
- 结果判断是否属于约定枚举。

当前要求 Node.js 20 或以上，仓库本身没有第三方生产依赖。

### Viewer 怎样工作

Viewer 是静态 HTML、CSS 和 JavaScript。启动本地服务后，它读取 Markdown、在浏览器内解析并生成三种阅读视角：

- 项目脉络：按时间浏览全部记录，关键版本或功能可以进入里程碑时间线；
- 复盘轨：集中看“假设—动作—数据—判断”；
- 决策手册：查看当前项目形成的稳定原则和证据。

它不需要打包构建。通过本地服务打开时，页面每 10 秒读取一次 Markdown，并在页面可见且内容变化时重新解析；这是一种不引入后端和第二份数据库的近实时更新。静态托管版本仍受部署边界约束：仓库或生成目录的新文件完成部署后，浏览器才可能读到更新。

记录详情会展示原话、需求、Agent 理解、计划、执行轨迹、依据和后来结果。Viewer 没有网页编辑器，也不会把输入写进浏览器缓存。页面里的“纠正记录”“补记后来结果”只会生成一句交给 Agent 的自然语言请求，真正修改仍由 Agent 写回 Markdown。

本地服务只监听 `127.0.0.1`，限制可读取路径，拒绝访问 `.git`、`.buildtrace`、`.env`、`node_modules` 和未列入白名单的根目录文件。

## Agent 的日常工作方式

项目初始化以后，用户不需要每次输入固定口令。Agent 应从普通对话中判断这轮是否产生了有意义的项目事实。

开工前：

1. 读取项目初心；
2. 找到与当前任务有关的历史记录；
3. 查看最近记录和已经到期的回看；
4. 分清哪些是用户确认事实，哪些只是旧摘要、产物证据或推断。

工作中：

1. 保留用户与本事项有关的完整原话；
2. 单独记录自己的当时理解和计划；
3. 用真实文件、提交、测试、截图或数据作为证据；
4. 如果计划改变，在执行轨迹中写出改变和原因；
5. 只有缺失信息会改变事实判断时才追问用户。

完成后：

1. 有意义的变化在同一轮写回 Markdown；
2. 小的机械变化并入相关记录，不制造噪音；
3. 需要等结果的动作写观察计划和日期；
4. 已经有后来数据时，补上结果判断；
5. 检查记录能否回答“为什么、做了什么、依据在哪、后来怎样”。

“自动”指项目规则驱动 Agent 在正常工作中主动读写，不是一个在后台偷听所有聊天的服务。

## 第一次安装与历史恢复

BuildTrace 分成用户级 Skill 和项目级记忆两层。

用户级安装只需执行一次。`buildtrace setup` 把独立、无项目档案的 Skill 链接到各 Agent 用户目录，并写入带明确起止标记的常驻自动激活规则；重复执行会原位更新，不叠加重复段落。全局启用不会在安装当天批量修改所有仓库，而是在以后第一次进入一个可写项目并开始有意义工作时触发该项目自己的初始化。

每个项目仍需单独初始化。初始化会：

- 创建该项目自己的 Markdown 主源；
- 安装项目内的 Skill、Viewer、解析器、恢复规范和 CLI；
- 写入 Codex、Cursor、Claude Code、GitHub Copilot、Windsurf 与 Gemini CLI 的项目规则；
- 已有 `AGENTS.md` 时先备份，再添加带标记的 BuildTrace 区块；保留原有指令，无需手动合并；
- 先运行一次本机历史审计；
- 不覆盖已经存在的项目主源。

当前历史恢复按以下范围工作：

1. 当前任务里仍能看到的完整消息、工具调用和上下文；
2. Agent 有相应应用工具时，分页读取仍可访问的 Codex 任务；
3. 本机 Codex 的 active / archived rollout 文件；
4. 本机 Claude Code 的 project session、compact、parent UUID 与 sidechain 线索；
5. compact 标记、可见的父子任务元数据和多 Agent spawn 关系；
6. Git 全部分支与提交，以及项目内可能的聊天导出、运营记录、截图和数据文件；
7. 用户授权连接或主动提供导出后，才读取 Cursor、聊天平台或其他外部来源。

本机审计会在私有目录生成 `.buildtrace/recovery/latest.json`。它记录搜索范围、匹配任务、来源哈希、消息引用、计数、父子关系和未解决缺口，不复制完整聊天，也不参与 Viewer 展示。

恢复内容必须标注保真度：

- `verbatim`：拿到了完整原文；
- `compacted-summary`：只剩上下文压缩后的摘要；
- `artifact-evidence`：只能从代码、提交、截图或文档确认；
- `inferred`：根据多个证据推断，尚未被原始来源确认；
- `unavailable`：知道可能存在，但现在无法访问。

当前实现能自动扫描本机 Codex rollout、Claude Code project session、Git 和项目文件，并读取原生暴露的多 Agent、parent UUID 与 sidechain 关系。应用内任务分页仍需要 Agent 调用相应工具；没有原生父子元数据的 fork 只能保守标为部分可恢复。已删除、无权限和从未导出的会话无法找回，任何 Agent 都不得把“扫描过能访问的来源”说成“恢复了全部历史”。

## 安装、同步和运行命令

以下命令是当前已经实现的接口：

```bash
# 从 GitHub 一键安装，并为常见 Agent 开启以后项目的自动初始化
npm install -g git+https://github.com/yimleunggggg/Buildtrace.git && buildtrace setup

# 给一个真实项目初始化 BuildTrace
buildtrace init --target /absolute/path/to/project

# 重新盘点当前仍可访问的历史来源
buildtrace recover --target /absolute/path/to/project

# 从主仓同步新版 Viewer、规则和脚本
buildtrace sync --target /absolute/path/to/project

# 在项目目录打开只读看板
buildtrace serve --target .

# 检查项目结构和记录合法性
node bin/buildtrace.mjs doctor --target /absolute/path/to/project
node bin/buildtrace.mjs status --target /absolute/path/to/project

# 导出可移植结构
node bin/buildtrace.mjs export --target /absolute/path/to/project --format json
node bin/buildtrace.mjs export --target /absolute/path/to/project --format jsonl

# 从多个项目生成个人决策手册
node bin/buildtrace.mjs playbook \
  --target /absolute/path/to/project-a \
  --target /absolute/path/to/project-b \
  --output /absolute/path/to/playbook.md

# 生成新的团队版或公开版静态目录
node bin/buildtrace.mjs publish \
  --profile team \
  --target /absolute/path/to/project \
  --output /absolute/path/to/empty-directory

node bin/buildtrace.mjs publish \
  --profile public \
  --target /absolute/path/to/project \
  --output /absolute/path/to/empty-directory
```

`sync` 只更新 BuildTrace 管理的规则、脚本和 Viewer，替换前会在 `.buildtrace/backups/` 保存备份。它不会改写项目自己的 `BUILDTRACE.md`；`AGENTS.md` 等共用指令文件只更新带标记的 BuildTrace 区块，区块之外的指令保留。

## 私密、团队与公开版本

每条记录都有 `private`、`team` 或 `public` 可见范围。旧记录安全地默认为 `private`。

私密版直接读取项目主源，只适合本地或严格受控环境。团队版和公开版不是在网页里用 CSS 隐藏内容，而是在生成阶段创建新的 Markdown 和静态站点目录：

- 团队版排除私密记录，移除任务来源、项目资料、绝对路径和本地 URL；可以保留团队可见原话和 Agent 过程；
- 公开版只包含明确标记为公开的记录，还会移除原话、Agent 内部过程、技术备注、项目资料、任务引用和内部路径；
- 生成后再次扫描常见本地路径和密钥形态，仍有敏感内容就拒绝发布。

团队快照仍需要部署在有访问控制的环境。任何派生版本都不能覆盖私密主源。

## 当前已经做到什么

当前版本是 `v1.18.0-alpha.1`，许可证为 MIT。

已经运行的部分：

- Markdown 唯一主源和 schema v3；
- 自然语言驱动的 Agent 记录规则；
- 用户原话、需求、Agent 理解、计划和实际执行的分层记录；
- 本机 Codex 历史、compact、多 Agent 元数据、Git 和项目证据审计；
- 只读三视图 Viewer；
- 项目资料分类和本地安全预览；
- 假设、动作、观察、数据与结果判断的复盘轨；
- JSON / JSONL 导出；
- 多项目决策手册；
- 私密、团队和脱敏公开派生；
- 项目初始化、同步、备份、校验和 GitHub Pages 部署模板；
- 在 BuildTrace 自身和 Yakushima Bus 两个真实项目中试跑。

仍需更多真实使用验证的部分：

- 不同 Agent 是否能长期稳定地从自然语言中自动摘取，而不过度记录；
- 一个月后用户是否真的会回来补数据和结果；
- 跨项目决策原则能否形成有证据的个人方法，而不是新的信息负担；
- Cursor 和其他 AI 工具的历史来源如何在得到授权后以同样保真度接入；
- 团队协作、冲突合并和长期规模增长时，单文件 Markdown 的使用上限。

目前没有云端账户体系、后台数据库、自动接入 GA4 / PostHog / Linear 的连接器，也没有持续监控指标的后台任务。结构已经为这些外部事件预留位置，但不能把未来能力描述成现成功能。

## 采用了哪些成熟模式

BuildTrace 先借鉴已经被真实用户验证的问题模型，再决定是否需要自己实现：

- Cline Memory Bank 证明了项目内文件可以承担跨会话上下文；
- Linear Projects / Updates 证明项目资料、阶段更新和健康状态需要放在一起；
- PostHog annotations 证明发布和产品动作需要标在数据变化附近；
- Apache DevLake、ONES 和 TAPD 证明跨工具事件、知识、里程碑和交付关系存在长期需求；
- amber.ac 给 Viewer 提供了克制、终端式、重视排版秩序的视觉参考。

BuildTrace 没有复制这些项目的源码或视觉资产。它与这些工具的差异，是把人的原话和假设、Agent 当时的理解与执行、项目证据和后来结果放进一条可审计因果链。如果未来实际引入第三方代码、资产或 schema，必须记录来源、版本和修改，并按原许可证处理；致谢不能替代许可证义务。

## Claude 读完后应该怎样理解自己的角色

如果 Claude 只是需要理解产品，到这里已经足够。

如果 Claude 要在一个安装了 BuildTrace 的项目中继续工作，应遵守下面的操作契约：

1. 先把 BuildTrace 当项目记忆层，不把它当 changelog 或任务列表；
2. 开工前恢复与当前任务有关的初心、历史、近期记录和到期回看；
3. 保留用户相关原话，不把原话、需求总结和自己的理解混为一谈；
4. 清楚区分计划与实际执行，计划变化要留下原因；
5. 每个事实给依据，推断标成推断，拿不到的来源写不可访问；
6. 有意义的工作完成后同一轮写回，小改动不要制造单独记录；
7. 不在 Viewer、JSON 或恢复清单里修改项目事实；
8. 不因为动作早于数据变化就声称存在因果；
9. 分享前生成独立的团队或公开派生物，不把私密主源直接上线；
10. 需要读取 Claude 自身旧会话时，先核对 `.buildtrace/recovery/latest.json` 中本机 project session 清单，再读取当前权限允许的相关消息；清单只证明来源存在，不代表已经完成内容映射。

一句话说：BuildTrace 不是替人记流水账，而是让人的判断、Agent 的行动和后来发生的事实，在项目里还能重新对得上。
