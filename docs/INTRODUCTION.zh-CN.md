# 我为什么做 BuildTrace

> 这是仓库内的简版自述。更完整的第一人称版本见[《AI 写代码越来越快，但不理解你为什么这么想，我想把“人的判断”留下来》](https://mp.weixin.qq.com/s/OBF-aNReio1grgVbTYSYzg)。

我不是工程师，读的是人文学科，做过多年用户运营、社区和线下活动。最近我用 AI 做了几个从自己兴趣出发的小产品：户外社交 Demo、屋久岛公交查询工具，以及行李和装备管理工具。很多时候，我就是自己产品的用户。

AI 把代码写得越来越快，项目却越来越容易“失忆”。Git 能告诉我哪天改了哪些文件，Agent 能总结这一轮完成了什么。但几周后再看数据，我经常想不起来：当时为什么要改？基于什么判断？原本期待什么发生？后来到底有没有发生？

真正容易丢的不是代码，而是人的原话、动机、假设和取舍。它们不一定是正式需求，却决定了项目为什么往这个方向走。上下文被压缩、会话切换以后，这些属于人的判断往往最先消失。

所以我做了 BuildTrace。它把人的原话和假设、Agent 当时的理解与执行，以及后来发生的数据和反馈，连成一条可以回看的因果记录。简单说：Git 记录项目变成了什么，BuildTrace 记录它为什么变成这样。

## 做得越快，反而越难复盘

我习惯从运营视角看项目，喜欢隔一段时间复盘数据。但 AI 开发把思考和行动分散到了很多地方：需求在一个对话里，代码在另一个 Agent 里，部署在平台里，数据又在 GA4、GSC、Bing 或别的后台。

跨日期看数据时，我经常想不起那个阶段具体做过什么。为了搞清楚“是哪件事让数据变了”，翻遍所有地方，也拼不出一条完整的因果链。最后只能看到两张截图：之前的数据和现在的数据，中间真正发生过什么却模糊了。

对话里还有很多很有用的原话：

> 我觉得 Bing 来的用户大概率是日语意图。
>
> 这个阶段先不管转化，先让页面被索引到。

它们不一定正确，却很重要。它们记录了当时的假设，也说明为什么会做后面的动作。Agent 有上下文压缩，工具之间不会自动继承完整对话，下一个会话开始前，这些带着“活人经验”的东西很容易就没了。

还有一些判断会反复出现。比如我如何处理信息层级、什么时候先看搜索收录、什么时候暂缓转化、什么样的界面看起来太像模板。这些并不是某次 coding 的结果，而是我的审美、逻辑和做事方式。它们值得长期留下，也可能在别的项目里再次被验证。

代码跑起来越来越容易，但人的判断、当时的假设和“我认为／觉得／猜测”反而越来越难留住。BuildTrace 就是从这里开始的。

## 我想留下的不是一份更新日志

一条有用的记录，至少应该把这几件事连起来：

```text
当时人的原话和假设
→ Agent 怎么理解、怎么拆解
→ 实际做了什么
→ 一段时间后发生了什么
→ 回头看，这个判断成立吗
```

Git commit 很擅长告诉我哪些文件变了，任务工具很擅长告诉我事情有没有完成，数据平台很擅长展示指标。BuildTrace 不需要把它们再做一遍。它要补的是中间那段因果：为什么采取这个动作，当时有什么依据，后来有没有足够证据支持原来的判断。

所以它现在的主数据不是一个藏在网页里的数据库，而是项目里的 `BUILDTRACE.md`。人和 Agent 都能读，Git 能追踪，换工具后也还在。看板只是这份 Markdown 的只读视图，不会反过来成为另一套事实源。

## 它现在怎么工作

第一次把 BuildTrace 装进项目时，它会先审计仍然能访问到的上下文：Codex 的当前和归档任务、compact 线索、多 Agent 来源、Git 的全部分支、项目里的聊天导出、README、运营日志和数据记录。它不会声称能凭空恢复已经删除或从未导出的对话；找到什么、没找到什么、哪些只是推断，都要写清楚。

之后我可以像平时一样和 Agent 说话，不需要先填表：

> 先把日文搜索页面收录做起来，两周后看曝光和点击，再决定要不要改转化。

Agent 应该保存这句原话，分清我的要求和它自己的理解，记录它计划的步骤、真正执行的步骤和验证证据。两周后如果数据到了，再把变化和我的结论补回同一条记录。一次动作于是可以慢慢长成一个 milestone，而不是在“已完成”那里结束。

看板目前有三个入口：

- **项目脉络**：按时间看发生过什么，保留标签、状态、资料和完整详情；
- **复盘轨**：把人的假设、实际动作、数据变化和结果判断摆在同一条线上；
- **决策手册**：把不同项目里使用同一稳定 ID 的判断汇在一起，仍然能点回原始记录，不让 Agent 自己编一套方法论。

记录还可以选择 `private`、`team` 或 `public`。本地私密版保留完整原话和过程；团队版只带明确允许协作的内容；公开版会在生成阶段去掉原话、内部路径、Agent 过程和项目资料。公开安全不能靠网页里“看不见”，因为交给浏览器的数据本来就可能被下载。

## 它适合谁

我最先想到的，是和我相似的人：不一定会写代码，但会用 AI 做真实产品；有自己的判断，也想看数据、做运营和复盘；项目可能散在多个 Agent 和平台里，又不想为了记录而维护一套沉重流程。

开发者也可以用，只是 BuildTrace 不会代替 issue、changelog、Git、Linear 或 PostHog。它和这些工具之间应该是链接、导出或连接器的关系。真正需要自己做深的，是人的原话与判断、Agent 执行、外部证据和后来结果之间那条链。

## 现在的阶段

BuildTrace 仍是 alpha。我正在用它自己和一个已经运营的真实产品持续试跑，检查它能否跟上长期迭代、数据复盘和不同 Agent 之间的切换。真实项目档案留在各自项目里，不进入公开仓库或安装包。

它目前能在本地安装、同步到多个项目、导出开放数据、生成个人决策手册，也能为团队或公开分享生成独立派生看板。跨工具的完整自动读取仍受各平台权限和导出能力限制，这部分我不会假装已经解决。

我想继续验证的只有一件很朴素的事：几周或几个月后，再看到一段数据变化时，人能不能沿着记录回去，知道自己当时为什么做、AI 实际做了什么，以及这次判断后来有没有成立。
