# BuildTrace 的下一步：跨工具的项目记忆与复盘

研究日期：2026-10-13。本文是产品与架构建议，尚未实施的能力不得写成当前功能或安装承诺。

## 产品定位

建议对外用一句话说明：

> 换 AI 工具、换电脑、隔几周再回来，仍能知道项目当时为什么这样做、做到了哪一步，以及后来有没有效果。

BuildTrace 的核心产品应是跨工具的项目记忆与复盘系统。Skill 是接入入口；本地记录服务负责保存、索引和同步；可选的复盘 Agent 负责检索与解释。

独立 Agent 适合“帮我回顾这个项目”“上次为何放弃这个方案”“上线两周后效果如何”等任务。原话采集、保存、去重、版本校验与同步不应依赖模型判断或每轮提醒。

Harness 通常包括模型运行循环、工具、上下文管理、权限和执行环境。BuildTrace 当前没有自己的完整 Agent harness。下一步需要的是记录、恢复和交接的运行机制；保留接入现有编程 Agent 的方式，优先复用成熟的会话采集能力。

## 官方资料支持的接入路径

| 来源 | 官方公开能力 | BuildTrace 应用方式 |
| --- | --- | --- |
| Codex | Hooks、App Server 的 thread / turn / item 与历史分页 | 经授权记录可取得的会话事件，按需读取相关历史；具体客户端、版本与事件覆盖须实测 |
| Claude Code | UserPromptSubmit、SessionStart、PreCompact、Stop、SubagentStop 等 hooks，以及 transcript 路径 | 提交时保留原文，结束时登记实际执行，在 compact 前检查采集游标 |
| Cursor | 会话、prompt、编辑、compact、stop 与 subagent hooks | 逐事件采集；IDE、CLI、云 Agent 分开给出支持范围 |
| Entire | 与 Git 对齐的会话 checkpoint、来源追溯与恢复 | 优先验证能否导入或关联其 checkpoint；若能满足采集需求，减少重复建设 |
| claude-mem | 自动采集、上下文压缩、检索和后续注入 | 借鉴采集与恢复模式；摘要必须链接原始证据，不能代替原话 |

## 推荐架构

```text
各工具 hooks / 授权导入 / 可读取的会话 API
                       ↓
              本地采集与写入服务
                       ↓
         原始证据保存 + 项目可读 Markdown
                       ↓
             可重建的索引和搜索
                       ↓
            总看板 / 单项目看板
                       ↓
             可选私有同步与远程阅读
```

不要求一次重构当前 Markdown 主源。先在现有版本旁建立原始证据层，业务记录继续由 Markdown 表达。

- **原始证据**：按原消息与附件保存，不由模型润色。消息正文与原始载荷分开标明；保留 source ID、内容哈希、采集时间和来源引用。附件应有实际文件或明确缺口，文件名不等于内容已保存。
- **项目记忆**：Markdown 保存值得长期回看的原话引用、当时判断、动作、证据和结果。摘要与解释有独立 ID 和来源。更正以追加记录表达。
- **索引**：SQLite / FTS 等承担跨项目查询和本地搜索，可以从源数据重建，不成为第二份可编辑事实库。
- **更新机制**：原始事件立即入队，经过去重与事务写入后通知看板。模型整理按轮次或后台合并执行，采集成功与整理成功分别呈现。
- **AI 接口**：CLI 或 MCP 提供检索、恢复上下文、提交补充和建立交接记录。MCP 负责调用入口，不自动获得其他工具的聊天历史权限。
- **并发控制**：新写入通过单一服务排队，记录版本号及预期基线哈希；基线变化时返回冲突。暂不改造的直接文件编辑应产生差异警报，不能被当作已验证写入。

这些都是下一版设计建议。当前代码仍以 Agent 直接编辑 Markdown 为主。

## 跨工具、fork、分支与设备

同一项目需要稳定 `project_id`。本地路径、Git remote、分支、worktree 和设备路径是别名及上下文，不单独作为项目唯一身份；复制仓库、fork 仓库和同一远端的独立用途可能需要用户确认归属。

每次活动应携带：

- `tool`、工具版本、能取得时的模型标识；未知就保留 unknown。
- `session_id`、`turn_id`、`message_id`，以及工具提供的 parent / fork / subagent 关系。
- `device_id`、workspace、branch、commit、事件发生时间、采集时间。
- 来源方式：原生 hook、官方 API、日志导入、用户手动补录、推断。
- 完整性：消息是否逐字匹配原始载荷、游标是否连续、附件是否存在、缺少哪些来源。

“发现 Cursor 和 Codex 都编辑了这个项目”可以自动记录；“Cursor 正式把任务交给 Codex”必须有交接事件或用户说明，不能只根据时间先后推断。

交接卡保存：当时目标、已完成 / 未完成事项、选择与放弃的理由、实际验证、待确认点，以及接收工具。一个项目可以有多条并行会话，界面以分支与会话泳道呈现，不强行拼成唯一线性故事。

恢复可读项目背景与恢复原工具执行环境是两件事。另一工具可以读取上下文并继续工作，但未必能原样恢复工具调用、运行中的任务和审批状态。

## 总看板和单项目看板

总看板首先帮助用户找回工作：

- 项目名称与最近有意义进展。
- 当前用过哪些工具、最近一条会话来自哪里。
- 采集是否正常、哪些工作已采集但尚未整理。
- 待继续事项、待补的关键判断、需要回看的真实观察计划。
- 最近同步时间、来源设备、冲突或离线状态。

单项目看板围绕“现在进行到哪里”组织：

1. 当前方向、最近一次重要决定、下一步与阻碍。
2. 关键版本、功能、交接和里程碑组成的时间轴。
3. 选中节点后展开人的原话、当时理解、计划、执行和证据。
4. 对需要验证的动作展示假设、基线、观察期与后来结果。
5. 活动 / 工具视图展示具体会话及分支，资料与部署留在菜单。

不默认展开全量聊天或每次文件保存。原始证据应可检索、可核验，项目时间轴只提炼有意义节点。

界面应分别显示“最后采集”“最后整理”“最后同步”。当前文件轮询只能证明读到了新的 Markdown，不能证明所有工具会话均已记录。

## 跨设备阅读和同步

| 模式 | 可以怎样使用 | 实时限制 |
| --- | --- | --- |
| 当前本地服务 | 当前电脑浏览器访问 localhost | 另一台设备的 localhost 指向另一台设备；目前服务仅绑定 127.0.0.1 |
| 私有远程访问 | 经现有带身份认证的网络 / 代理访问原电脑服务 | 原电脑和服务必须在线；不能只放开端口就宣称安全完成 |
| 私有同步看板 | 本地服务把授权记录同步至自托管或可选托管端，手机登录阅读 | 原电脑离线时可看最后同步内容；恢复联网后补传 |
| 公开静态看板 | 生成脱敏快照并部署到固定 URL | 部署更新后才出现新内容，通常不等于秒级同步 |

建议第一版跨设备先支持只读。第二台电脑也编辑项目时，事件具有独立设备与来源 ID，冲突保留双方版本；不采用最后保存者覆盖。Git 适合版本化的项目记录，原始会话与本地忽略的快照需要独立、可选择的同步和备份策略。

## 安装体验与开源发布

第一版向用户提供“一次安装、自动发现、验证记录”的引导：

1. 检测已安装的工具和具体客户端版本，给出可用接入能力。
2. 选择允许记录的工作目录；已有项目自动发现，新项目在授权根目录内首次活动时登记，支持排除与临时暂停。
3. 选择是否导入旧历史；展示来源范围与缺口，扫描发现不等于已经恢复。
4. 发送一条测试消息，确认原始采集、项目关联、Markdown 整理和看板展示四步各自成功。
5. 打开固定总看板入口。项目页面挂在同一服务下，减少多个终端和端口。
6. 跨设备同步作为可选设置，不阻碍本地使用；基础采集和回溯无需模型 API key。

未来可设计 `buildtrace open` 打开总看板，`buildtrace open --project <id>` 打开项目。以上命令尚未实现；当前仍用 `buildtrace serve --target <project>`。

开源交付建议：

- 保留 MIT、清晰贡献指南和 issue 模板；通用程序、适配器、契约与合成测试数据公开，个人档案独立存放。
- 发布带版本 tag 的 GitHub Release 和固定版本安装路径，明确 alpha / beta；npm 包名与账号权限核验后再发布到 registry。
- README 只承诺已验证的能力，并分别列出工具 / 客户端 / 平台 / 版本的采集、恢复、交接支持程度。
- 提供 60 秒演示：旧项目导入 → 换工具继续 → 手机回顾 → 误改恢复。
- 采用成熟项目的代码前，核验精确版本和文件许可证，按要求保留 LICENSE / NOTICE；模式致谢与源码复用分开记录。
- 招募少量真实用户，在不同工具组合和设备上完成同一组任务，再决定能否承诺“自动记录所有项目”。

## 实施顺序与发布门槛

1. **可靠采集**：接入已验证的 hooks 或现有 checkpoint，保存原消息和游标，支持失败补传与明确缺口。
2. **多项目与交接**：稳定项目 ID、注册 / 发现、单服务总看板、工具来源与会话关系。
3. **完整性保护**：覆盖无稳定 ID 的旧记录，验证快照哈希、固定可信基线、原子写入 / 锁、并发冲突与异常警报。
4. **上下文恢复**：按任务检索相关原话、未完成工作和原始证据，生成可携带的交接包。
5. **跨设备只读**：私有同步、离线队列、最后同步状态；随后再考虑多设备同时编辑。
6. **结果复盘**：优先导入现成分析、发布、用户反馈数据，再增加连接器；AI 可提问和组织证据，人确认判断。

应验证的场景包括：更换工具不丢目标、compact 后原文仍可查、fork / 多 Agent 不重不串、并发写入无静默丢失、原电脑离线时手机仍可看最后同步内容、卸载后原始档案可带走。

## 当前实现边界

本地已有 Skill、CLI、项目 Markdown、单项目 Viewer、历史清单、快照 / 恢复和原话格式审计。全局项目注册、统一总看板、完整 hook 采集、同步端与跨设备实时访问尚未实现。

现有 `audit-quotes` 检查的是记录内声明的来源与 fidelity，尚未逐条比对会话原始载荷，也没有核对某次任务的全部用户消息是否都进入记录。因此不能把通过比例称为原话完整率。

现有 `verify-history` 是修改后检测：它比较选定快照与当前解析结果，只覆盖带稳定 ID 的部分历史字段，不能阻止任何有文件权限的 Agent 直接写文件。当前快照也不是操作系统层面的不可变存储。原始文件和快照都在同一台机器，仍需要独立备份。应先补齐这些机制，再承诺长期防丢。

## 2026-10-16 补充：不要把作者用法变成所有人的用法

本次定向核对国内 V2EX、海外 Reddit 的原始讨论，以及官方仓库的用户问题和成熟实现。它是质性需求盘点，不是全网抽样调查；发帖者有自选择偏差，部分分享者也是同类工具作者。讨论能证明有人遇到问题，不能证明问题占比、付费意愿或 BuildTrace 已解决问题。

| 直接反馈或成熟模式 | 对 BuildTrace 的设计判断（推断，不是调查结论） |
| --- | --- |

| [V2EX：Vibe coding 的维护与责任](https://v2ex.com/t/1208240)，4 月不同使用者对 Demo、生产系统和交接持不同看法 | 小工具与团队长期项目分层；保留验证、已知限制和交接线索，但不替代测试、审查及责任判断 |

### 应保持一致与应允许不同

- 通用底线：真实来源、项目隔离、时间与版本可查、追加纠错、缺口可见、授权后分享。
- 项目可选：分类名称、展示顺序、何种变更值得独立记录、是否需要假设/指标/复盘、分享方式。运营实验只是场景之一。
- 依规模渐进：个人小工具先能找回上下文；持续产品关注方向变更和发布验证；团队/并行 Agent 增加来源、分支、冲突与交接，不默认把每个人都带入复杂管理系统。
- 三种记录层级：原始证据可检索；普通修复在工作记录中可找；关键时间轴只保留值得回顾的阶段变化。完整记录不等于默认铺开全部消息。

### 下一轮验证，先测任务而非征求功能愿望

招募非技术创作者、独立开发者、小团队维护者与多 Agent 使用者，覆盖国内外工具组合。让他们独立完成：安装后核验一条原话；隔几天找到当时拒绝的方案；换工具继续同一任务；定位一项调整何时开始；并行工作不串项目；误改后找回旧版。记录完成时间、需要求助次数、漏记/误记、隐私误分享与运行成本。样本覆盖不等于代表全球，达不到就收窄发布承诺。

当前优先级仍是可靠采集与恢复、统一项目入口、冲突/回溯和清晰安装。更细的互动变化链、可选阅读模式及跨设备服务要分别实现和验证，不把这份建议当已交付功能。
