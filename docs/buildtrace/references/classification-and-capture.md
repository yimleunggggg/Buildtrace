# 记录选择、分类与补记规则

## 通用底线与项目偏好分开

不伪造证据、不混项目、保留历史与纠错依据，是通用底线。某一位用户的阅读顺序、分类名称、记录粒度、运营指标和做事习惯，不自动成为所有项目的强制规则。默认选项应有多类真实使用场景支持；项目可以自定义。社区反馈是需求线索，不是“所有开发者都需要”的统计结论。

小工具、长期维护的产品、多人项目与并行 Agent 工作流需要不同的重点：按任务读取相关上下文，不在每轮灌入全部历史；无假设、指标或后续观察需要时，不强迫填写结果实验。代码审查、发布和运行状态优先引用已有系统，不另造一份状态。

## 先判断是否值得留下，再保存完整原话

项目记忆不是聊天备份。值得记录的是会改变目标、用户体验、规则、实现、运营动作或后来判断的信息：需求、顾虑、假设、取舍、确认的决定、具体失败反馈、实际动作与结果。

- “怎么了 / 如何了 / 继续 / 收到”在仅催进度、续接或礼貌确认时，不新建节点，也不提升为核心原话。短句不天然无价值：“不要公开”是重要约束；“同意”若确认了关键取舍或授权，也要连同所确认的对象留下。
- “打不开”是问题反馈。它可以成为相关修复的依据，但重复反馈并入同一问题，不把每次催问铺成独立产品判断。
- 从一条有实质内容的消息里选中要记录的事后，保留该条完整原文，不重写、拼接或冒充逐字摘录。流程性元数据、自动注入的 Skill、屏幕树和环境上下文不是用户原话。
- 图片先判断用途：真实错误/数据证据、设计参考、示意图，还是装饰/重复附件。记下它证明什么、不能证明什么及来源；示意图不证明功能已实现，参考图不证明用户已选择全部方案。不要只抄附件路径或未经核对的 OCR。
- 旧档案里的“用户要求 / 用户指出”通常是 Agent 转述，除非核到原始消息，不标为逐字原话。留在历史摘要层，不删旧证据。
- Agent 当时理解只来自当时公开表达的说明；计划来自当时公布的计划，执行来自实际工具调用、修改与验证。未记录就写“未取得当时记录”。不要提取或展示私有推理，也不要把完成后的认识改写成当时已知。

## 两个独立维度

大类 `领域` 回答“改的是哪块”；第二层 `动作` 回答“做了哪类事”。它们不是父子树，例如界面与交互既可新增、优化，也可修复。不要把“产品决策、UI、AI 工作流”当作同一套工作对象分类。

默认大类：`interface` 界面与交互、`product` 产品逻辑、`backend` 服务与接口、`data` 数据与内容、`growth` 运营与增长、`delivery` 发布与运行、`workflow` 开发与 AI 协作、`system` 系统架构。

默认动作：`add` 新增、`improve` 优化、`fix` 修复、`decide` 决策、`research` 调研、`analyze` 分析、`restructure` 重构、`publish` 发布、`review` 复盘。

按实际影响判断，不按提到的工具名或文件后缀判断：管理后台换布局归界面；权限接口归服务；支付规则归产品逻辑；支付转化实验归增长。跨领域允许多个稳定 ID。无法判断就留待分类，不为了齐全猜测。

每个项目可在自己的记录源中增加 `## 分类规则`，覆盖某一维度的默认选项；格式如下。每条写清范围、排除项或例子，Agent 在记录前读取。删除选项只对后续分类生效；旧记录保留原 ID，改名沿用 ID。全局模板更新不能覆盖项目自定义规则。

```md
## 分类规则

- [area | interface | 界面与交互 | Interface & UX] 页面、视觉、文案、交互；不含接口权限。
- [area | content | 内容生产 | Content production] 稿件、编辑与素材；不含发布系统开发。
- [action | improve | 优化 | Improve] 改善现有能力；不把新增能力混进来。
- [action | fix | 修复 | Fix] 修复可复现问题，保留现象和验证。
```

记录中使用 `领域: interface`、`动作: fix`。旧 `场景` 兼容保留；Viewer 对旧场景的映射只是阅读兼容，不等于已经重新审计分类。

## 简明重点与完整细节

新记录可增加 `动机要点` 和 `行动要点`：只压缩已有事实，使用具体对象与动作，例如“保留旧指令”“补上项目定位”。不新增动机、成果或因果。完整 `为什么做`、`做了什么`、原话和执行步骤仍保存。未写要点的旧记录只能显示带标识的原文摘录，不能伪称已提炼。

## 互动之后，究竟调整了什么

按可核对的关系留下“用户消息 → 当时公开理解/整理 → 原计划 → 实际动作 → 反馈后的调整”，使用已有 Q/R/U/P/E 引用关联；没有当时理解就标缺口，不能事后补成当时已知。反馈使方向改变时，在执行轨迹追加日期、触发消息、改变了哪个对象、原方案与新方案，以及验证依据。保留原计划和先前结论，不把来回调整改写成一次顺利完成。

记录日期不自动等于最早开始日期、上线日期或补录日期。跨日期工作在执行轨迹写有证据的实际日期；只能定位时间范围时写范围，找不到则写未知。补录需注明何时补入与事件何时发生。后续独立的重要调整用新记录链接旧记录 ID，避免把几个月的变化都塞回一个旧日期；同一轮零碎修边并入相关执行步骤。关键节点只放重要版本、功能、架构变化、发布及确认里程碑，普通问题修复仍可搜索，不因没上时间轴而丢失。

## 补记先定位，不能随便丢给任意项目的 AI

补记请求至少携带项目名称、记录 ID、日期、标题；本地看板还携带实际档案路径、项目根目录、当前分支和仓库。接收 Agent 先核对身份、源路径及 ID，再保存快照并追加带日期的结果。无权限、找不到、跨工作树版本不同，都先报告候选/冲突，不写入碰巧打开的其他项目，不自动新建替代记录。

## 全量发现与取舍不是一回事

旧记录没有稳定 ID 时，不把 Viewer 按位置生成的临时索引冒充已存编号。按档案、日期、完整标题唯一定位，歧义先确认；核实后才补稳定 ID，再做结果更新。

先发现相关来源，再选择值得留的事件。恢复扫描应包含 `git worktree list --porcelain -z` 所列工作树、共同 Git 目录、所有可见分支、当前与归档会话、显式父子关系的传递闭包，以及用户确认属于同项目的旧路径。可用 `recover --project-alias /旧项目路径` 补充搬迁/未建 Git 的早期目录。

来源清单必须区分：找到、实际读取、映射为记录、跳过及原因、未映射、不可访问。来源数量不是恢复完成率；旧文件目录的日期也不是记录事件日期。Git 记录只能证明提交，不证明动机或上线。外部工具、删除的工作树和未导出的聊天仍须如实标缺口。

模式参考：Git 的 [worktree 清单](https://git-scm.com/docs/git-worktree)与共同仓库关系；GitHub 的[可自定义标签名称、说明及颜色](https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels)。这里只借鉴信息模式，未复用第三方代码。
