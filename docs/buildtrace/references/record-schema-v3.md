# BuildTrace record schema v3

兼容扩展：新记录的事项 ID、阶段、讨论过程、交付与检查、可选字段及阅读层级见 [事项与阅读结构](matters-and-reading.md)。以下旧格式继续读取，不要求新记录重复填写所有小节。

v3 在 v2 的证据链上增加三类可选结构：复盘轨、跨项目决策原则和发布可见范围。`docs/buildtrace/BUILDTRACE.md` 仍是唯一可编辑主源；JSON、个人决策手册、团队快照和公开快照都只是可重新生成的派生物。

## 分类、重点与证据选择（向后兼容扩展）

可选字段 `领域` 与 `动作` 分别记录工作对象和动作类型；项目可在 `## 分类规则` 自定义稳定 ID、名称和判断范围。`动机要点`、`行动要点` 是基于原记录的简短重点，不替换完整 `为什么做` / `做了什么`。细则见 [记录选择与分类规则](classification-and-capture.md)。旧场景仍保留；未知或已停用分类不能使历史记录消失。

原话元数据可加 `purpose=approval|decision|constraint|evidence|coordination`，用来区分有后果的简短确认和纯进度交流，不能据字数机械丢弃。来源 fidelity 与用途是两个维度：完整转述仍不是逐字原话。只记录公开的 Agent 说明、计划和行为，不恢复私有推理。

## 可见范围

每条记录可以声明：

```md
可见范围: private | team | public
```

- `private`：完整私密记录，可包含原话、内部路径、Agent 过程和项目入口。旧记录没有此字段时一律按 `private` 处理。
- `team`：允许进入团队快照。生成时仍移除私密记录、任务来源、项目入口、绝对路径和本地链接；团队快照必须放在有访问控制的环境中。
- `public`：允许进入脱敏公开快照。生成时还会移除沟通原文、Agent 内部过程和技术备注。

公开分享必须运行 `buildtrace publish --profile public` 生成新目录。只在浏览器里隐藏内容不是安全边界，因为原始 Markdown 仍可能被下载。

Agent 只能在用户明确表达共享意图时把记录标为 `team` 或 `public`；不能根据内容“看起来不敏感”自动公开。

## 关键节点与普通记录

每条记录可以显式声明：

```md
关键节点: 是 | 否
```

- 默认是 `否`。普通修复、同一功能的修边、文案与间距微调仍可留在记录或既有执行轨迹中，但不进入项目脉络总览。
- `是` 只用于主要版本、重要功能、架构转折、正式发布或已经确认的项目里程碑。
- 关键功能上线和项目里程碑不是同一事实。前者可以成为关键节点；“达到 1,000 用户”等里程碑必须有外部证据确认。
- Viewer 只用这个字段决定项目脉络展示，不根据标题、状态或最近完成时间自动猜测。

## 复盘轨

没有对应内容时可以省略这些可选小节。不要为了填满结构而发明假设、指标或结果。

```md
人的假设:
- [H1] 如果把人的判断和动作放在同一条记录里，之后的数据复盘会更容易归因。

观察计划:
- [W1 | 指标=回看完成率 | 数据源=项目记录 | 基线=未记录 | 目标=连续 3 次完成 | 窗口=30 天 | 达成规则=到期后有数据和明确判断] 验证这条复盘轨是否真的被使用。

数据变化:
- [D1 | 日期=2026-08-18 | 指标=回看完成率 | 值=3/3 | 变化=从未记录到连续完成 | 来源=项目记录] 三条到期记录均补上了后续结果。

结果判断:
- [O1 | supported | 日期=2026-08-18] 观察期内成立，继续使用。
```

结果判断的推荐标签是 `supported`、`refuted`、`mixed`、`inconclusive` 或 `pending`。它描述某条假设后来是否成立，不替代记录级的 `结果状态`。

同一条记录可以先只有假设和观察计划，后来再追加数据变化与结果判断。必须保留前后时间与证据，不能用后来认识重写最初假设。

## 追加式历史与纠错

- `记录 ID`、记录日期、既有沟通原文、需求总结、Agent 当时理解、原计划和执行轨迹属于历史证据，不做静默覆盖。
- 新结果、补充证据和纠错可以追加到原记录；如果旧判断有误，保留旧说法并写明修正时间、来源和新判断。
- 修改前运行 `buildtrace snapshot --target .`，修改后运行 `buildtrace verify-history --target .`。校验发现记录删除或既有证据被改写时失败。
- `.buildtrace/history/` 按内容哈希保存本地快照并按源文件隔离。同一仓库可以同时保护公开演示和私有真实主源，不允许交叉选择基线。
- `buildtrace restore --snapshot <hash-prefix> --confirm` 恢复前先保存当前版本，因此误改版本和目标旧版本都可回溯。
- `buildtrace audit-quotes` 只报告原文 provenance；它不得把摘要、附件说明或不可访问历史改写成逐字原文。

## 决策原则

真正需要跨项目复用的判断使用稳定 ID：

```md
决策原则:
- [dp-human-judgment-first | 分类=产品 | 确认=user-confirmed] 工具降低实现成本时，更要保留人的判断、假设和取舍。
```

- ID 必须是 `dp-` 加小写英文、数字或连字符。
- 同一条原则在不同项目里沿用同一个 ID，标题或表述微调时不要随意换 ID。
- 只有真实记录明确支持时才添加原则，不要从相似文案自动推断。
- 只有用户明确确认、所属记录 `来源可信度: confirmed` 且有依据的原则才能添加 `确认=user-confirmed` 并进入个人决策手册。Agent 自己概括的候选不得冒充用户方法。
- `buildtrace playbook --target <project-a> --target <project-b>` 按 ID 聚合证据。
- 同一 ID 出现不同表述时标记为冲突，交给人确认；程序不能擅自融合。

## 可迁移派生物

- `buildtrace export --format json|jsonl`：完整私密结构化导出，schemaVersion 为 3。
- `buildtrace playbook`：跨项目原则索引，证据仍链接到各项目记录。
- `buildtrace publish --profile team|public`：从主源生成一个新的、只读、已脱敏静态目录。

派生物不能反向覆盖主源，也不能被 Viewer 或 Agent 当成第二份项目事实。
