# BuildTrace

这个文件是项目记忆的唯一主源。Agent 在这里记录，Viewer 只读展示。

## 作者的话

最近几个月，我围绕自己的兴趣密集地做了几个 vibe coding 项目：户外社交软件 Demo；在日本徒步时因为找不到路而做的交通信息查询工具（上线 1.5 个月，800+ 用户，60% 来自自然搜索）；还有户外行李和装备管理 Demo。很多项目都从“我自己就是用户”开始，再根据真实使用一点点调整。

我读的是人文学科，做过多年用户运营、社区和线下活动，所以比起工具本身，我更在意机制背后人的需求和原因。如果只是因为某个工具就做成了一件事，说明这件事本身的价值也不高，功劳是工具的。做出来以后，那个项目是谁的？是人的好奇、人的判断、当时对话里“我觉得应该这样”让它走到这里，还是 AI 把它堆出来，人只是在旁边点了几次确认？

让人着迷的是那些生而为人的本能。人的好奇、思考、审美、热爱，它会因为工具变成更多形状和方式。

- 运营视角，爱看数据复盘。但是在跨日期看数据变化时候，有时候想不起来那个阶段内自己做了什么，尤其是在思考，对话，开发可能在不同的vibe coding工具里的时候，自己很难记清干了个啥，这样数据复盘时候就很难总结“成功/失败”经验，是什么让数据变化了，归因很难找（ 要复盘，要归因，想搞清楚"是哪件事让数据变了"，翻遍所有地方，拼不出一条完整的因果链）
- 很多有价值的信息，出发点/动机，都是难得的“活人经验”和人的主观性反馈，都在对话记录里， 而Agent又有compact总结等机制， 不记录的话很快消失了。比如聊天记录里有很多真实的判断——"我觉得bing来的用户大概率是日语意图""这个阶段先不管转化，先让页面被索引到"——这些话是有用的，但它们在下一个会话开始之前就被压缩了，消失在上下文里。
- 很多思考和做事方式是有固定思考方式的，包括从其他人经验看到后，临时在agent对话里体现，这些”出发点“才是每个人的做事方式，然后才形成coding结果和实体。这个思考过程和启发过程，是值得留存的，很多可以长期复用到其他项目上。（审美/逻辑/决策方式）

AI 做项目的问题。代码跑起来越来越容易，但人的判断、当时的假设、"我认为/觉得/猜测"反而越来越难留住。

## 项目初心

- 为什么做这个项目: 不让人的出发点、判断、取舍和行动因果埋在 AI 对话与上下文压缩里。
- 面向谁: 用 AI 做产品、但不一定有成熟工程流程的运营、增长、内容、独立开发者和 vibe coding 用户。
- 目前最重要的判断: 先把 Markdown 主源、Agent 工作流和只读 Viewer 做成可信闭环，再考虑云服务和多项目总览。
- 不想做成什么: 不做普通 changelog，不强迫用户填长表，不维护第二份浏览器数据库，不假装能够恢复不可访问的历史。
- 成功大概长什么样: 几周后用户和新 Agent 都能快速知道当时为什么做、依据在哪、后来是否有效。
- 产品方法: 不从空白想象功能；先确认成熟产品或开源项目已经验证的用户需求，再选择复用、接入或只借鉴模式。
- 借鉴边界: 不重做任务管理、知识库、产品分析或 DevOps 数据湖；原创投入放在人的原话与判断、Agent 执行、外部证据和后来结果之间的可审计因果链。

人的假设:
- [H1] 对长文本项目记忆而言，减少同时出现的阅读面、提高基础字号和分隔线可见度，比继续增加卡片、颜色和状态数字更能改善长期回看。
- [H2] 只有把项目脉络限制在未来仍值得单独找到的关键变化，时间轴才会形成方向感；普通修边应进入相关记录的执行轨迹，而不是继续增加同级节点。
- [H3] 复盘轨列表应该帮助人快速判断是否值得点开，而不是在列表层承担全文阅读；四步摘要与完整详情分工后，因果顺序会比四列长文更容易扫读。

为什么做:
- 用户回看的核心是“这个项目为什么这样走到现在”，不是判断所有记录当前处于哪个抽象状态。界面必须先帮助人阅读，再提供需要时才出现的资料、部署和纠错工具。
- 项目记忆如果把每个小改动都提升为节点，会迅速退化成另一份变更日志，掩盖真正的版本、功能、架构转折和后来成果。

做了什么:
- 形成两列阅读、按需详情、克制灰绿和更大字号的新可读性基线。
- 将作者内容改成可选、只显示一次的第一人称层；项目概览改为全部记录、关键节点、需要补结果和最近记录。
- 将资料、部署、纠正和结果补记改为次级但可发现的工具，并修复两个真实交互故障。
- 在主源、解析器、模板、Skill、schema、设计说明和使用手册中建立关键节点门槛。
- 将复盘轨列表收成四步摘要和条数，完整记录仍从同一 Markdown 主源进入按需详情；没有删除原话、Agent 理解、计划或执行证据。

观察计划:
- [W1 | 指标=用户连续阅读时的主观清晰度 | 数据源=用户对真实 BuildTrace 与 Yakushima 看板的后续反馈 | 基线=用户明确反馈“眼睛很累、可读性弱” | 目标=不再需要依靠缩放或反复寻找主线，并能说清资料、部署、纠正和补结果入口 | 窗口=2026-07-19 至 2026-07-25 | 达成规则=用户实际回看后确认更容易读，且没有再次报告入口闪退或公共文档 Forbidden] 验证这次调整是否真正降低阅读和操作负担。
- [W2 | 指标=复盘轨首屏可扫读性 | 数据源=用户查看新的四步摘要后的直接反馈 | 基线=用户反馈“太挤了，排版也有些乱” | 目标=不展开详情也能分清假设、动作、数据和判断，需要完整内容时再点开 | 窗口=2026-07-23 至 2026-07-25 | 达成规则=用户确认复盘轨不再拥挤，且能从摘要正确选择要查看的完整记录] 验证列表与详情的分工是否符合真实回看习惯。
